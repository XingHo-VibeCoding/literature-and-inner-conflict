# 文学与内心冲突｜回滚手册

日期：2026-10-20（Asia/Shanghai）。所属任务：Day 26。
本日只实操静态托管回退；云函数回退、数据恢复是备查流程，未执行不能填写成功。实际演练见 [记录与模板](rollback-drill-day26.md)。

## 1. 何时启动回滚

- 新版发布后首页白屏、入口或关键JS/CSS缺失，或总结／书单等关键路径无法打开。
- 新版引入可重复的核心功能失败，影响原文、日期、版本保护或取消删除等已有保障。
- 新版明确导致健康／接口5xx、CORS回归或前后端契约不兼容，无法及时安全恢复。
- 怀疑隐私泄露、越权或错误写入时立即停止扩大操作、保留证据并联系负责人；静态回退不等于已处置泄露或恢复数据。

记录发现时间、URL、实际HTTP/错误原文、影响范围及最近一次发布版本。先判断故障是否由本次发布引入；401过期会话、单次网络失败不能单独证明需要回滚。
明确回退对象是前端、函数、配置还是数据。回滚代码不会恢复已删除或改坏的数据；恢复前端也不会切换云函数版本。

### 什么情况必须回滚

判断顺序：先核对实际错误与发布版本，再选择故障所在层。出现数据或隐私风险时先停止相关访问／写入，不能为了复现反复写库。
下表要求回滚时，仍须先按第2节确认目标、备份和兼容性；没有安全可用的旧版时，先止损并制定恢复方案，不盲目切换。

| 看到什么情况 | 判断依据 | 是否必须回滚 | 先做什么、回退哪一层 |
| --- | --- | --- | --- |
| 新版白屏、入口或JS/CSS缺失，关键路由打不开 | 实际HTTP、资源类型或页面错误可重复；已确认新版引入，旧版资源完整且兼容当前API | 是，回退静态前端 | 保留URL、错误与资源哈希；先核对旧资源，最后恢复旧index.html，再验证公网 |
| 页面和health均正常，但已有保存／回看等核心流程失败 | 相同虚构输入可重复失败；证据确认新版引入，旧版流程正常且兼容 | 是，回退已定位的故障层 | 不能只看页面打开或HTTP200；保留业务结果与错误，避免重复提交，再按静态／后端故障选择回退路径 |
| 新版破坏原文／日期，取消删除仍发请求，或发生错误写入 | 有直接请求／结果证据，或虚构示例可重复复现；已确认与新版有关 | 是，先止损再回退有缺陷的层 | 停止相关写入；确认旧版保留数据保护后回退。已损坏数据另行评估，代码回退不会修复数据 |
| 新版出现越权、私人数据误展示或凭证暴露 | 有可信直接证据；不能用真实他人数据继续试验 | 必须立即止损；有已核验安全且兼容的旧版时回退 | 停止受影响访问并保留脱敏证据；处置故障层。凭证撤销、权限核验等另行处理，页面回退不能撤回已泄露信息 |
| 新函数／网关配置引入持续5xx、CORS失败或契约不兼容 | HTTP、requestId及发布差异能定位到函数或配置；不是仅凭一次health失败推断 | 是，回退已确认的故障层 | 核对旧函数／配置与当前前端、数据兼容性；静态回退不能代替后端恢复。本日仅按第5节备查，不实操 |
| 只有已有用户会话过期的401 | 错误明确指向身份；重新准备有效会话后恢复，未发现新版回归证据 | 否，先处理会话 | 使用既有登录流程，不改数据库权限、不扩大CORS、不把401当空列表 |
| 单次超时／网络失败，或新旧版本都受同一上游故障影响 | 只有孤立请求，或证据指向共同依赖；尚不能归因本次发布 | 不直接回滚 | 保留时间、HTTP／网络错误、requestId并定位依赖；停止重复写入，不用前端回退掩盖上游故障 |
| 轻微样式偏差，核心路径、原文保护和隐私均正常 | 问题局限于外观，不妨碍阅读和操作；没有功能或安全影响 | 通常否 | 记录问题，等用户决定修复范围。若影响关键按钮可用性或误操作，重新按上方功能／数据风险判断 |
| 找不到可信旧包，旧版不兼容当前数据结构，或旧版有已知安全缺陷 | 备份、版本／哈希或兼容性核对不通过 | 禁止盲目切回 | 停止扩大故障，补齐安全恢复目标或另定修复方案；不把“必须处置”理解成“随便退一个版本” |

## 2. 开始前必须确认

1. 用户确认目标：上一可用发布产物、源提交（未知写未知）、入口／资源哈希和备份目录。不能把 HEAD~1 自动当上一公网版。
2. 当前 v1.0 的可恢复产物也已保存；原线上入口和全部引用资源均有本地备份。
3. 回退版与当前API／数据结构兼容；存在破坏性迁移或安全已知缺陷时，不盲目恢复旧前端。
4. 本次只切换静态入口，保留数据库、认证、密钥、CORS和云函数现状；如需改其他层，重新明确授权。
5. 准备计时与证据；不删除旧资源、不清空托管、不清理浏览器本地数据。

## 3. 静态托管回退：本日实操路径

本项目使用 CloudBase 静态文件管理。可靠回退是恢复已备份的 index.html 及其匹配资源，不以“上传提示成功”或看起来像旧页面作为完成标准。

1. **开始计时**：在第一次执行线上回退动作前记北京时间与计时起点 T0。登录、下载备份等准备时间单列。
2. 打开既有环境 → 静态网站托管 → 文件管理，核对公网域名及根目录。
3. 核对旧入口引用的全部资源仍在云端且哈希相同；缺失时先将备份资源按原相对路径补齐。保留v1.0资源。
4. 最后将备份的上一版 index.html 覆盖到根目录。不要把整个源码目录或 _logs 上传。
5. 等待部署生效；浏览器在原公网URL重新加载。若缓存仍旧，先记录入口哈希和响应，再用正常刷新／平台现有缓存更新能力处理；不要忽略错误或无限重试。
6. 公开HTTPS读取根入口、JS、CSS并与旧版清单逐项比较；确认不是200提示页或HTML冒充JS。
7. 同一公网页面确认标题、首页、关键路由与健康正常；旧版已知功能差异单独记录，不能用健康200代替私有数据验证。
8. **结束计时**：全部上述旧版检查通过时记 T1，回退耗时=T1−T0（秒）。同时记录可见等待和失败时间，不用估计值代填。
9. 保存公网页面、实际版本清单、提交记录和命令输出。源Git历史保持不变是这条回退路径的预期结果。
10. 进入第4节恢复v1.0，演练结束不能把旧版留在线上。

同名文件上传会覆盖，控制台路径以真实界面为准，依据 [CloudBase 文件管理](https://docs.cloudbase.net/hosting/quick-start)。CLI一致性部署另有备份能力，但本轮不安装CLI、不切换发布方式；不能把未执行的 --safe 写成已备份。

## 4. 恢复 v1.0

1. 记录恢复开始 T2，使用发布时封存的同一份v1.0产物，避免重建引入另一版本。
2. 核对v1.0资源仍在；缺失先补资源，最后覆盖v1.0的 index.html。
3. 按第6节验证公网入口、所有JS/CSS哈希、浏览器页面及health；运行完整现有检查，报告使用新的 day26/post-restore 名称。
4. 全部规定项通过时记录 T3，恢复耗时=T3−T2；演练操作总耗时=T3−T0。准备耗时另列，不混入回退恢复时间。
5. 保存复验结果，明确线上最终为v1.0；不以本地源码已恢复冒充公网恢复。

## 5. 云函数回退（只备查，不实操）

目标函数是既有 literature-health、literature-reads，不能随意回退到仅支持读取的早期reads包。

1. 用实际错误与requestId确定受影响函数，核对函数版本、HTTP路由指向和前后端／数据库兼容性。记录现状，停止重复写入。
2. 在该函数的版本管理检查是否存在已验证的数字版本；LATEST会随更新变化，不能当不可变备份。记录旧版本的代码、运行时、入口及非秘密配置摘要，秘密值由平台保管。
3. **有兼容旧数字版本且当前入口支持版本路由时**：在现有灰度／流量配置将流量切回该旧版本；逐项核对HTTP触发器、服务路径和实际版本指向，防止只改版本列表未改线上路由。
4. **只使用LATEST或无旧版本时**：从可信的已验证旧部署包恢复原函数代码，保留现有身份验证、精确CORS和秘密配置；重新部署到原函数。没有可信旧包就停止，先补齐证据，不假装可一键回滚。
5. 等平台显示部署正常后，验证health及受影响接口；reads需要已有普通测试会话、精确路径/响应/数据核对。真实写入验证另获授权且只用虚构记录，不用管理员Key代替用户会话。
6. 验证失败保留错误、时间、requestId，停止循环重试；恢复刚记录的上一状态也需要可用产物与明确目标。

版本与流量机制依据 [CloudBase 云函数灰度发布](https://docs.cloudbase.net/cloud-function/gray-release)。具体HTTP触发器是否支持目标版本，以该环境实际控制台为准；本轮未查看或修改函数版本，未宣称已验证该回退路径。

## 6. 回滚／恢复后验证

| 检查 | 通过标准 |
| --- | --- |
| 线上身份 | 同一公网域名的根入口及实际JS/CSS引用、SHA256与目标备份完全一致 |
| 页面 | 首页标题、排版、导航正常；总结与书单路由可打开且刷新不白屏 |
| 健康 | /api/health HTTP200、JSON中 ok=true，service精确为【literature-and-inner-conflict】 |
| CORS | 允许来源为精确静态Origin；entries允许来源预检204，禁止来源403且无ACAO |
| 数据保护 | 本轮不发云端POST/PATCH/DELETE、不做SQL恢复、不清IndexedDB；有授权会话才另做私有数据读核 |
| 恢复v1.0 | 现有 verify-project 全项PASS；若含失败／未验证，明确记录，不能只写“恢复成功” |

回退旧版本时，当前源码构建与旧版不一致是预期；版本判据改为“旧线上资源＝回退备份”，不要重建旧源码后伪装当前源码一致。恢复v1.0后必须再次满足当前构建与线上一致。

## 7. 数据恢复（只备查，不实操）

本项目云端核心表为PostgreSQL entries，另有浏览器IndexedDB本地数据。静态文件备份、Git与数据库备份不是同一件事。
若确有数据损坏：停止进一步相关写入、保留当前数据及时间证据，核对实际PostgreSQL备份成功时间与可恢复范围，明确哪些新数据可能丢失并请用户拍板。先在隔离目标恢复、核对ID／原文／日期／版本／关联与权限，再制定生产切换方案；不得直接覆盖生产或恢复平台管理的身份数据。
本轮仅写方法；没有取得备份记录、没有恢复到隔离目标时，恢复能力、恢复点与恢复耗时均记未验证。平台能力参考 [CloudBase PostgreSQL备份说明](https://docs.cloudbase.net/en/database/postgresql/faq)。

## 8. Git 安全回退与降级

本轮静态入口切换不撤销源码提交，也不新建中途commit。
若将来确需撤销某个代码提交：先核对用户指定目标、工作区与父提交；用 git revert 生成保留历史的反向变更，再按任务规定确认文件后提交和部署。合并提交须先辨认主线，不能盲目套命令。恢复已revert的修改也需明确选择反向revert或新修复提交。
禁止 git reset --hard、强推或移动发布标签来掩盖历史；仅执行git命令不会自动改变公网静态站点。

卡住时优先保留已验证发布；回退受阻则至少尝试到有证据的“退回上一版”并记录实际状态。若已退回但恢复v1.0失败，明确提示当前线上是旧版，不能把演练写完成。登录、上传、缓存或网络同操作反复失败就停下报告，不循环尝试。
