# 文学与内心冲突｜发布前检查

在包含 package.json、deploy-day20.md 的 my-app 目录执行。用户提供其他项目时，先依据其真实记录和命令适配，不套用本项目服务名、域名或历史结论。

## 执行方式

```powershell
# 当前项目实跑；报告只保存在被 Git 忽略的本地目录。
node .agents/skills/verify-project/scripts/verify.mjs --report day25/check-20261020-1
```

默认公开地址取自 deploy-day20.md；更换已确认的发布目标时使用 `--site HTTPS来源 --api HTTPS来源`，不读取真实 .env 内容。构建命令会由现有 Vite 按项目配置加载本机环境，报告不能打印这些值或完整环境列表。

每次使用先读项目 AGENTS.md、Git 工作区状态及下面涉及的踩坑记录；检查本地可用的 Node/npm。遵守现有改动与提交边界，证据不足的项目不能报 PASS。脚本是按需手动运行的工具，不安装定时任务、CI 或发布钩子。

## 结果与证据

- 每个实际检查输出 `PASS` 或 `FAIL`，包括命令/HTTP方法、退出码/状态、计数/资源哈希等证据、通过标准和核验边界。
- 缺工具、网络异常、构建失败、读取失败或依赖项失败均为 `FAIL（未验证或阻塞）`，不凭历史结果补成通过。一次失败原样保留；重跑生成新报告，不覆盖前一轮证据。
- 任一项FAIL，总结果FAIL。全部自动项PASS仅表示“本轮列出的自动检查通过”，不能宣称已验证整个产品或已具备发布条件。
- 本轮没有有效普通用户会话和专门业务操作证据时，私人数据、云端角色权限、真实CRUD与跨设备持久化写明“未验证”。本地模拟测试通过不等于真库通过；health200不能代替entries200。
- 不读取/输出真实.env、密钥、密码、Authorization或私人记录。不为截图新建云端数据，不运行旧 verify-day18/19 的真实写入模式。
- 机器可读JSON、Markdown及浏览器HTML只放 `_logs/`；每轮使用新的报告名，同名报告必须拒绝覆盖。提交中不含日志、构建产物或故障临时文件。Git历史扫描只读取当前项目路径在本地现有可达引用中的内容，不冒称远端已同步或未知格式秘密绝不存在。

## 两轮反馈与故障验证

1. 首轮用当前公开地址实跑，保留报告，逐条核对命令与判据。独立复核只指出有证据的误报/漏报；没有发现就如实写“在已核验场景中未发现”，不编造检查器Bug。
2. 使用虚构响应在内存验证：200提示页、JS地址返回HTML、错误健康服务名、通配CORS、空测试、执行失败不能PASS；本地地址不能当公网。
3. 把发现的判据问题修正在本Skill或脚本，再按同样标准跑第二轮。真实项目失败保留为失败，不改业务功能、不放宽标准凑全绿。
4. 故意把本次检查输入设为本机地址，证明公网项会FAIL而非虚报：

```powershell
node .agents/skills/verify-project/scripts/verify.mjs --site http://localhost:5173 --report day25/fault
```

该故障仅模拟“发布目标错误地指向本机”，不是公网服务宕机，也不证明密钥扫描能识别所有秘密。不要修改线上或真实.env。保存故障证据后，恢复默认地址再运行第二轮。

本地HTML报告可在已运行的Vite地址下打开，例如 `http://localhost:5173/_logs/day25/fault.html`。让用户在同一画面看见故障输入、对应FAIL与证据；报告页面不是线上产品。没有拿到截图文件时，只能说页面已展示，不能声称截图已保存。
